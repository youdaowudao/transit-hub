# V2.0.5 业务基线回退与无关功能回收

## 目标 / 需求快照

### 人类原本希望解决的目标

从 `V2.0.6` 开始引入的 Priority 压力控制，以及随后加入的安全熔断、canary 和异常队列，已经改变了原有健康调度行为，并出现一次短暂失败后长期停滞、状态显示与实际调度不一致的问题。本次先把业务代码恢复到已经确认可接受的 `V2.0.5` 起点，再把与这条问题链无关、已经存在且可用的功能收回，形成一条可以在本地验证、正常推送和合并的干净开发线。

### 本次目标

1. 以 `V2.0.5 (d193eec)` 作为业务代码内容锚点。
2. 保留 A：健康档位、workspace 全局排序和跨分组 target 去重等旧 Priority 行为。
3. 移除 B、C、安全闸门、canary、异常队列、D、E、F，以及只服务于这些机制的依附项：`7651c1a` 安全闸门说明和 `9829978` B/E 写回窗口修复。
4. 恢复已经确认与安全熔断无关的功能，包括手动探活取消、上游管理页面修复、站点启用与首页成本容错、有效倍率、历史失败显示、主站调度确认等。
5. 完整恢复 `V2.0.11` 的一键升级与一键回滚合同，使服务器继续复用既有维护脚本、systemd 单元、状态文件和配置路径。
6. 保留现有迁移文件和数据库兼容记录；本次不执行数据库清理、迁移回退或数据恢复。
7. 形成新版本 `V2.1.13`，不复用 `V2.0.5`、`V2.1.11` 或 `V2.1.12` 版本号。

### 成功标准

- 最终运行代码不包含 B/C、安全闸门、canary、异常队列和 D/E/F 的有效调用链。
- A 的旧健康状态机和 Priority 行为可在本地定向验证。
- 无关功能按行为恢复，不因从 `V2.0.5` 重建而丢失。
- 一键升级和一键回滚的前端 API、后端 API、systemd 执行器、部署脚本、状态文件和互斥合同完整匹配。
- 迁移 runner 面对现有 `000019` 至 `000024` 记录不报错，不执行 down migration，不清理数据库。
- 本地固定 `dev` 与新回退提交一致；远端发布阶段只允许后续由用户推送 `origin/dev` 并创建 `dev -> main` 普通 Merge commit。

### 明确不做

- 不在本次实现“失败两三次后再停用”的新确认机制。
- 不重写健康状态机，不设计新的安全阀门，不引入 canary 或新的队列。
- 不保留 B/C 的 probe、reconcile、writeback 三循环、pending 合并、写入节流和跨 workspace 压力控制。
- 不保留 D 的预算、公平、队列和 reservation；不保留 E 的分批写回；不保留 F 的轮次统计。
- 不修改 PostgreSQL 数据、删除多余表列、删除 `schema_migrations` 记录或执行 `pg_restore`。
- 不强推、删除、重建远端 `dev`，不操作 `origin/main`，不创建或合并 PR。
- 不修改服务器、systemd、Docker、Redis 或 Sub2API 远端状态。

### 固定约束与风险

- `V2.0.5` 是内容锚点，不是新提交的版本号。
- 新回退提交应以 `origin/dev=9829978` 为父，避免把本地尚未推送且已决定废弃的 `V2.1.11/12` 发布到远端；旧本地线必须先建立仅本地归档。
- 一键回滚只回滚源码和构建产物，不回滚数据库。遇到破坏性迁移或迁移文件不完整时，既有回滚门禁必须拒绝执行。
- `000022_upstream_site_enabled.sql` 是保留的 V2.1.0 站点启用功能的运行依赖，字段读写和迁移必须完整保留，不能按残留结构处理。
- `000019`、`000020`、`000021`、当前源码中的 `000023` 和 `000024` 作为迁移与一键回滚兼容记录保留；它们不代表恢复对应的 B/C、安全、E/F 运行逻辑。D 专用 `000023_connection_health_priority_pressure_d.sql` 不在当前 dev 祖先树中，不重新加入源码，数据库既有残留也不在本次清理。
- 本次工作区已有 safety 未提交改动和另一个 worktree 的暂存改动必须分别保留，不能覆盖、丢弃或混入目标提交。
- 另一个 worktree 的动态间距功能属于后续独立迁移：它保留 A 的方向，但当前实现依赖将被删除的 B/C/E/safety 代码形态，不能直接合并到 `V2.1.13`。
- `docs/` 默认被 ignore；本变更四份文档必须在提交边界报告后显式纳入 `V2.1.13`，不能因普通 `git status` 不显示而漏交。
- 本方案中的“历史干净”固定指：远端 `dev` 只做 fast-forward、`main` 使用普通 Merge commit、不 force-push、不改写祖先，最终运行树不含被否决功能。本方案不删除已经发布的 `4bd2523`、`b548344`、`ced2a1a` 等历史提交；要抹除这些祖先只能重写远端历史，明确不做。
