# 实施方案

## 1. 总体方法

不使用从 `V2.0.5` 新建分支后再合并的方式，也不逐个 `git revert` 当前 38 个提交。两种做法都不能可靠地从当前树删除已经互相耦合的 B/C、安全、D/E/F 代码。

本次使用“目标树重建 + 普通前进提交”：

1. 保留当前本地 `dev=db436763`、已有 stash 和其他 worktree 的引用作为归档证据。
2. 从 `origin/dev=982997804` 建立独立临时 worktree。
3. 以 `V2.0.5` 还原业务代码，再按本文件的保留清单收回无关功能。
4. 将最终目标树作为一个新的 `V2.1.13` 前进提交；目标提交父级是 `origin/dev`，不是本地废弃的 `V2.1.12` 线。
5. 本地验证完成后停止，远端推送和 PR 由用户另行操作。

这样远端 `dev` 仍可从现有远端提交普通 fast-forward，既不改写远端历史，也不会公开本地三条尚未推送的 safety 修复。

“干净”只描述新线路拓扑和最终内容：已经发布到 `origin/dev`/`origin/main` 的 B/C/safety 提交仍保留为祖先，由 `V2.1.13` 的前进提交删除其运行内容。禁止为了让日志中看不到旧提交而 rewrite 或 force-push。

## 4. Git 与工作区顺序

1. 记录 `pwd`、当前 worktree 列表、`dev`/`origin/dev`/`origin/main` SHA 和工作区状态。
2. 为 `db436763` 建立仅本地归档引用；当前 dirty safety diff 与 `stash@{0}` 分别记录哈希和内容摘要。
3. 保留 `/tmp/transit-hub-health-priority-spacing` 的 16 项暂存改动，不复用、不清理、不移植。
4. 在第三个 `/tmp` worktree 从 `origin/dev` 建立临时重建分支。
5. 先物化 V2.0.5 业务树，再按第 2 节逐项收回；生成路径白名单和禁止路径清单。
6. 更新代码内版本、前端 package 版本、生产 compose 镜像版本和本次变更文档为 `V2.1.13`。
7. 运行目标代码的定向后端、前端和部署脚本静态检查；不运行服务器命令，不访问远端。
8. 同时生成两份机械差异：目标树相对 `V2.0.5` 的增加项必须落在保留白名单；目标树相对 `origin/dev` 的删除/修改项必须落在禁止功能或版本元数据清单。任何触及保留功能文件的删除都必须逐项解释并由对应行为测试证明未丢失。
9. 本地验证通过后才允许创建 `V2.1.13：回退 V2.0.5 业务基线并收回无关功能` 提交；本轮不推送、不建 PR。
10. 后续由用户自行推送 `origin/dev`、合并 `dev -> main`，服务器只从最终 `origin/main` 安装。

## 5. 既有动态间距 worktree 的后续收回

`/tmp/transit-hub-health-priority-spacing` 当前有 16 项暂存改动，约 `+1235/-69`。该任务的用户目标、公式和行为已经确认，但代码直接修改了 B/C/E/safety 之后的 `priority_strategy`、checkpoint、分批写回测试和签名合同，不能整份 merge 或 cherry-pick 到新的 V2.0.5+A 线路。

固定处理顺序：

1. `V2.1.13` 完成并通过本地验证前，该 worktree 原样保留，不 reset、不取消暂存、不提交、不清理。
2. `V2.1.13` 收口后，从新的本地 `dev` 建立另一个隔离迁移分支。
3. 以原 worktree 的 `01-SPEC.md`、公式、测试用例和 staged diff 为来源，只重接“健康档相对倍率动态间距”本身。
4. 新实现只能消费 V2.0.5+A 的 Priority 计算与写回合同，不得重新引入 B/C/E/safety 的 checkpoint、分批槽、pending 签名或 mutation generation。
5. 对原 worktree 的每一项行为建立新旧对照；确认公式、跨组聚合、90/91 边界、输入完整性门禁和详情排序等价后，才允许形成后续独立版本。
6. 原 worktree 在新提交完成且内容归属逐项确认前不得删除；是否清理由用户在后续任务决定。

该阶段不是 `V2.1.13` 的一部分，本次不提前修改动态间距代码，也不占用本次回退提交的版本号。

## 6. 数据库与服务器边界

- 首次回退不做 DDL 清理，不删 `schema_migrations`，不删除安全队列、D/E/F 表或列。
- 服务器重装前必须只读盘点 `enabled=false` 站点、非空 pending 字段、健康状态、Priority checkpoint、远端 Sub2API status/schedulable/Priority。
- 备份必须在升级脚本清理范围之外另存；数据库备份不能代替远端 Sub2API 状态快照。
- 服务切换必须确认真实 systemd unit、cwd、环境和 DB/Redis 目标；旧服务停稳后再安装新构建，避免两个调度器并行。
- 新服务启动后核对版本、健康接口、数据库身份和迁移记录，并观察首次调度及至少一个后续周期。
