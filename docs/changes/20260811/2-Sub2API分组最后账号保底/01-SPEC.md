# Sub2API 分组最后 active 账号保底

## 目标 / 需求快照

### 人类原本希望解决的目标

Sub2API 分组内多个账号连续失效时，健康模块可以自动把故障账号写成 `inactive`，但绝不能把一个分组的最后一个 `active` 账号也关闭。最后留下的账号即使仍不健康，也必须继续按原调度周期探活；以后出现其他 active 账号或自身恢复时，系统必须继续重新判断，不能停在长期熔断、等待 canary 或不再探活的状态。

### 本次目标

1. TransitHub 健康调度器执行自动 `inactive` 前，保证目标所属每个 Sub2API 分组都还有其他 active 账号。
2. 同组多个账号并发失败时，最多关闭到剩余一个 active，不能因并发判断同时通过而归零。
3. 复用现有 target 执行前完整刷新结果完成保底判断；保底不得增加主站读取或写后 readback。
4. 被保底的账号只跳过当前一次 `inactive` 写入；健康状态继续如实记录，后续探活与恢复状态机继续运行。
5. 已经归零的分组，只允许从能够证明由健康模块关闭的账号中恢复一个；不得自动开启用户手工关闭的账号。
6. 计划交付版本为 `V2.1.14`。

### 成功标准

- 保留 scheduler target 执行前的 `findAdminTargetWithMemberships` 完整刷新；本次不得删除、弱化或以旧 tick 快照替代它。
- 每次自动 inactive 候选只使用这次已有刷新得到的全部分组、账号和成员关系；不得再发第三次清单请求，也不增加写后 readback。
- 单账号分组连续失败多轮，主站 `inactive` 调用始终为 0，但该账号的探活时间和健康事件持续推进。
- 两个或多个 active 账号在同一轮同时失败，自动关停后每个分组至少保留一个 active。
- 同一账号属于多个分组时，只要任一所属分组只剩它一个 active，就不得关闭。
- 本轮跳过不产生跨轮阻断状态；下一次到期探活仍从新的执行前刷新重新计算，不依赖 safety gate、canary、队列或长期 reservation。
- `inactive` 写入超时、报错或进程中断后，当前轮次不继续消耗同组名额；下一轮按已有刷新结果重新核对并继续。

### 固定行为

- “保留一个”只约束健康模块自动写入的 Sub2API `status=inactive`。
- active 的判定以目标执行前刷新得到的账号 `status=active` 为准。`schedulable` 是独立人工开关，本次不自动修改。
- 状态机继续如实把故障目标记为 `suspended`；不得为保底伪造 `healthy`。
- 保底跳过不得写入 `pending_status=inactive`、`last_applied_status=inactive` 或其他“已经关停”的检查点。
- 上轮写入结果不明确但下一次刷新确认目标仍为 active 时，如果本次因最后 active 被保护，必须清除旧 `pending_status=inactive`，不能保留虚假的待执行状态。
- 保底结果可以写事件和展示，但事件、文案和 `last_remote_action` 不得参与下一轮调度资格判断。
- 正式手动探活可以更新健康状态，但不在请求线程直接写 `inactive`；已由健康模块停用的账号恢复健康时，保留既有的手动探活写回 `active` 行为。一次性隔离探活继续不写状态、不触发远端动作。
- 用户显式执行的调度开关、人工禁用和直接在 Sub2API 主站进行的操作不属于本次自动保底范围。

### 主站读取边界

- 保留当前调度轮开始的 workspace inventory 读取，用于生成探活任务。
- 保留当前每个 target 获得 target lease 后的执行前完整刷新，用于校验账号、成员关系、策略、状态和本次保底。
- 保底判断只复用第二项已经存在的刷新结果；不得为计数、关停前确认或写后确认增加任何新的分组/账号清单请求。
- 本次不实施“每 workspace 每轮只读取一次清单”的读取优化；它是独立长期事项，见 `docs/initiatives/阶段规划/20260811-未完成任务-分组健康调度清单读取优化.md`。

### 明确不做

- 不删除或替换 `AdminProbeTarget`、target lease、执行前刷新和现有探活任务生成机制。
- 不恢复旧 safety gate、canary、survivor、floor reservation、异常队列或安全 worker。
- 不建立持久化的“最后账号”所有权，不指定某个账号永久保底。
- 不修改失败阈值、冷却、观察、恢复状态机或 Priority 计算与写回。
- 不修改 Sub2API 主站代码、接口或数据库。
- 不自动修改 `schedulable`，不自动开启无法证明由健康模块关闭的账号。

### 已知边界

- 本次保证的是 TransitHub 健康调度器不会主动把分组从一个 active 降到零；用户或其他系统在执行前刷新之后、主站写入之前直接修改主站状态，仍是现有链路已有的外部竞争窗口。
- 保留执行前刷新确保不会因为 job 排队或本轮初始清单陈旧而扩大该窗口；本次不以减少读取换取更长的信息延迟。
- 清单不完整时不能证明最后账号安全，当前次自动 `inactive` 必须跳过；后续到期探活会重新刷新和重试，不形成永久阻断。
