# 手动探活并发排队

## 目标 / 需求快照

### 人类原本希望解决的目标

分组健康的正式手动探活在并发名额满时会立即失败，用户只能反复点击重试。用户希望点击一次后自动排到现有探活任务后面，名额释放时继续执行。

### 成功标准

1. 正式手动探活在全局或当前 workspace 名额满时等待，不再立即返回“并发已满”。
2. 手动请求已经等待时，新的自动探活不能继续插到它前面。
3. 关闭弹窗、离开页面或请求取消后，等待立即退出，不占用名额、不继续探活。
4. 全局并发 `5`、每 workspace 并发 `2` 保持不变，任何路径不得突破上限。
5. 同一目标仍受 target lease 串行保护，状态、事件和远端动作保持原有正式探活合同。
6. 前端必须明确显示正式探活当前处于“正在排队”或“正在进行”；若立即取得名额则直接显示“正在进行”，不得让用户静默等待。

### 明确不做

- 不增加并发上限，不修改探活间隔、每日预算或单轮任务上限。
- 不建立数据库持久队列、独立 worker、重试任务或服务重启后的队列恢复。
- 不修改健康状态机、Priority、`schedulable`、自动停用/恢复规则或执行前清单刷新。
- 不恢复已回退的 safety、canary、异常队列或相关 workspace 设置。
- 不处理一次性隔离探活和模型发现的并发控制。

### 固定约束与风险

- 等待队列只存在于当前后端进程内，并受 HTTP 请求 context 控制。
- 调度器按“并发名额 -> target lease”执行；手动探活必须使用相同顺序，不能在持有 target lease 时等待名额。
- 手动等待优先只阻止新的自动任务插队，不中断已经执行中的自动探活。
- 多个手动请求都必须最终获得名额或随各自 context 取消；本次不向前端展示精确队列位置和预计等待时间。
- 正式探活增加流式进度事件；旧 JSON 探活接口继续保留，避免影响既有调用方。
