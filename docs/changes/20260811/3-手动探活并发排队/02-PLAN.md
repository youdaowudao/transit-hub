# 实施方案

## 后端并发闸门

1. 将现有通用 `acquire(wait)` 拆成自动探活和手动探活两个明确入口。
2. 继续用全局 `5`、每 workspace `2` 作为共同硬上限。
3. 手动入口登记等待者并阻塞到名额可用或请求 context 取消。
4. 存在可等待的手动请求时，自动入口不再取得新名额；已运行任务正常结束并释放名额。
5. 名额释放、手动取消或等待状态变化时唤醒等待者；释放函数必须保证只执行一次。

## 正式手动探活

1. 完成 target 归属解析后先进入手动等待，再取得 target lease。
2. 正式探活通过流式事件通知前端排队和进行中状态；用户关闭弹窗时沿用 `AbortSignal` 取消请求。
3. 获得名额后的模型过滤、状态更新、事件、Priority 同步和远端动作合同保持不变。
4. context 取消不再映射成“并发已满”；handler 由现有请求结束路径处理，不发出真实探活。

## 前端进度反馈

1. 正式探活使用流式接口接收 `queued` / `running` / `result` / `error` 事件。
2. 弹窗在排队期间显示“正在排队”，取得名额后显示“正在进行”；一次性测试维持原有本地测试状态。
3. 关闭弹窗会中止流式请求，后端等待随请求 context 取消，不留下排队项。

## 验证与收口

- 定向测试覆盖：硬上限、手动等待、自动不插队、释放后继续、取消后退出、重复释放安全和流式进度事件。
- 前端补充排队/进行中状态行为断言，并运行 `npm run typecheck` 与构建检查。
- 运行 `go test ./internal/modules/connection_health -count=1` 和 `git diff --check`，不运行全仓测试。
