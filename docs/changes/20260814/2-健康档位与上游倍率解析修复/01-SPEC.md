# 健康档位与上游倍率解析修复需求

版本目标：`V2.2.5`

## 目标

- 账号健康状态变化后，即使本轮拿不到可靠倍率，也必须进入正确的 Priority 健康档，不能继续停留在旧的暂停、待探活或降级档。
- 上游 Key 列表必须完整翻页，避免绑定 Key 不在第一页时被误判为缺失。
- 页面必须直接说明倍率解析失败的具体原因和实际排序结果。

## 需求快照

- 健康探活策略继续遵守“健康档位第一、同档倍率第二”。倍率不可用只影响同档内倍率排序，不再阻止健康档位写回。
- 唯一可靠的上游有效倍率仍优先使用；`unassociated`、`missing`、`conflict` 有唯一有效本地回退倍率时，继续按本地回退倍率排序。
- 没有可用倍率时不猜 `1x`，也不读取真实连接中的历史分组倍率。账号固定落到当前健康档末位：
  - Sub2API：健康 `99`、恢复中 `999`、降级/观察 `9999`、待探活 `99999`、暂停/禁用 `100000`。
  - NewAPI：使用现有各健康档最低调度位，不跨越现有健康档边界。
- `unavailable` 仍不使用本地回退倍率，避免一次临时查询失败触发未经确认的倍率重排；但必须按当前健康状态进入对应档末位。
- `multiplier_only` 保持原合同：缺少主站分组倍率时不接管、不写回，也不改变其独立 Priority 区间。
- Sub2API `/api/v1/keys` 和 NewAPI `/api/token/` 都必须从第一页开始连续读取，直到上游总数已满足或出现正常末页；任一中间页失败时整次解析失败，不把不完整列表当成完整结果。
- 页面在没有实际有效倍率时显示 `-`，并区分：未关联真实连接、Key 分组或倍率缺失、多 Key 或分组冲突、本轮上游查询暂不可用。文案同时说明账号已按当前健康档末位排序。

## 成功标准

- 健康账号从 `10000` 或 `100000` 恢复时，即使倍率缺失或上游查询暂不可用，也会写入健康档末位，而不是保持旧值。
- 降级、恢复中、待探活和暂停状态在相同条件下都进入各自正确档位。
- 倍率恢复后，账号重新参与同健康档内的倍率和延迟排序。
- 绑定 Key 位于第二页或更后页时，Sub2API 和 NewAPI 都能找到该 Key，不再误报 `missing`。
- 页面不再同时展示历史倍率和“倍率不可用”的矛盾信息，且能直接看出具体原因。

## 明确不做

- 不修改 Sub2API、NewAPI 或其他上游站点源码。
- 不改变健康状态机、探活阈值、失败计数、远端停用/恢复、`schedulable`、手动 Priority 冲突保护和同步租约。
- 不改变 `multiplier_only` 语义，不新增倍率配置或数据库字段。
- 不使用真实连接保存的历史分组作为倍率回退，不做模糊分组匹配。
- 不做前端布局或视觉重构。

## 固定约束与风险

- Priority 是主站全局调度值；倍率未知时只能落健康档末位，不能给出看似精确的档内顺序。
- 分页读取必须继承现有请求上下文，调度取消后立即停止，不能遗留后台请求。
- 上游分页元数据缺失时，以不足一页作为结束条件；连续满页设置现有同类读取使用的安全上限，超过上限返回无效响应，不静默截断。
- 上游 Key 明文不得写入日志、同步状态、测试输出或前端响应。
