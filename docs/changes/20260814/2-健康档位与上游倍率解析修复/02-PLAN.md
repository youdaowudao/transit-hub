# 健康档位与上游倍率解析修复计划

## 1. Priority 写回

1. 保留现有上游倍率和本地回退倍率解析规则。
2. 健康探活策略无可用倍率时仍加入托管集合，按现有健康状态计算档位，并直接生成该档末位 Priority。
3. 有可用倍率的目标继续使用现有 `(健康档位, 有效倍率, 成功延迟, 稳定目标 ID)` 排序。
4. 无可用倍率时不覆盖同步快照中已有的历史有效倍率；新接管目标不伪造倍率。管理页面只展示本轮实际解析出的有效倍率。
5. 保留上游 Priority 为空、人工 Priority 冲突、未完整读取分组清单和策略退出恢复原值等保护。

## 2. 上游 Key 完整分页

1. Sub2API Key 列表使用 `page` 和 `page_size=100` 连续读取，保留创建时间倒序参数。
2. NewAPI Token 列表使用 `p` 和 `page_size=100` 连续读取。
3. 有 `total` 时必须读足总数；没有 `total` 时读到空页或不足 100 条的末页。
4. 复用当前请求上下文和认证参数；任一页请求失败或分页结果明显不完整时返回错误。
5. 增加两种平台第二页 Key 的回归测试，并保留现有取消请求测试。

## 3. 页面解释

1. 后端不再用同步快照中的历史倍率填充本轮无来源的 `effectiveMultiplier`。
2. 前端复用现有倍率列，根据 `multiplierResolutionStatus` 显示精确原因。
3. 无可用倍率时显示 `-`，文案说明“已按当前健康档末位排序”；本地回退和正常上游倍率文案保持原有含义。
4. 增加前端源码行为测试，固定四种状态及档末位文案。

## 4. 版本与验证

1. 将后端内置版本、前端包版本同步为 `V2.2.5` / `2.2.5`。
2. 先检查 diff，再运行 connection health 定向 Go 测试、upstream 分页定向 Go 测试、对应前端 Vitest 和 typecheck/build。
3. 每轮测试结束立即确认无测试服务器、worker、临时端口或临时文件残留。
4. 按重启前记录的启动器、工作目录、数据库和 Redis 连接重启固定 `5444`、`5555` 服务。
5. 重启后核对端口、健康检查、项目归属、数据库集群/库/用户、工作区和关键数据数量。

## 风险与回滚

- 风险：倍率不可用期间，账号会在正确健康档的末位运行，调度位置可能与旧的冻结值不同；这是本次明确修正的生产行为。
- 风险：Key 数量较多的站点会增加分页请求次数；请求按顺序执行并受现有上下文约束，不增加后台并发。
- 回滚：代码回退后恢复旧的冻结行为和第一页查询；本次不涉及数据库迁移，无数据结构回滚。
