# 实施计划

## 1. 服务器只读基线

- 确认实际服务、数据库、当前工作区和事件表，不猜容器、连接串或部署目录。
- 记录刷新接口端到端耗时，并拆分管理员分组、普通分组、上游站点同步、Key/Token 分页和本地 SQL 阶段。
- 记录事件表行数、时间分布、表和索引大小，以及三个最新事件查询的 `EXPLAIN ANALYZE`。
- 先判断瓶颈属于上游请求、数据库历史查询，还是二者叠加；本地测试只作为对照。

## 2. 查询与远端读取减负

- 为三个最新事件读取设计有明确时间边界或等效的最新状态读取方案，并用索引/查询计划验证。
- 检查管理员分组逐个读取上游账号、Key/Token 的分页和重复读取，优先采用已有上下文、批量或短时缓存能力；不得改变返回语义。
- 保留可取消的请求上下文和现有错误传播，不把超时或 500 改写成成功。
- 为刷新阶段记录可观测耗时，避免以后只能看到一个长转圈。

## 3. 24 小时事件清理

- 先在本地或测试环境验证删除条件、批量大小、重试和并发影响。
- 生产执行前备份待删除行并记录行数/指纹；按批次删除 `created_at < now() - interval '24 hours'` 的事件。
- 清理后核对当前健康状态、策略、动作、预算、站点、账号和工作区数量未变化。
- 执行普通 `VACUUM/ANALYZE` 的必要性评估；不在本变更中执行 `VACUUM FULL`。

## 4. 验证与上线

- 跑定向后端/SQL 测试和本地刷新前后对比。
- 在服务器先做只读或影子核验，再小批量清理，观察刷新耗时、错误率、数据库锁和磁盘空间。
- 确认滚动 24 小时内事件、当前错误详情和当前调度状态仍可用。
- 若远端请求仍占主要时间，单独排队上游请求优化，不把所有问题归因到事件表。

## 5. 回滚

- 查询/索引变更：停用或回退对应查询路径，保留原错误传播。
- 清理变更：从本次备份恢复被删除事件，停用清理任务；恢复后重新核对计数和时间分布。
- 任何需要大锁、停机或 `VACUUM FULL` 的操作，另立高风险任务并单独审批。
